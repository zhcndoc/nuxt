Nuxt 4.7 已发布，自 v4.6.4 以来包含约 350 次提交。🎉

这次发布带来了多项改进。您可以试用 Nitro v3，将应用的操作提供给浏览器中的 AI agent，在查看运行时错误的同时看到类型错误和 lint 警告，还可以用 schema 验证运行时配置。整体速度也有所提升，尤其是服务端渲染、水合和安装。

## 📣 一些消息 {#some-news}

### 现在就试用 Nitro v3 {#try-nitro-v3-today}

本次发布最大的变化是，您现在可以用 [Nitro v3](https://nitro.build) 构建 Nuxt 4 应用（[#37101](https://github.com/nuxt/nuxt/pull/37101)）。Nuxt 5 基于 Nitro v3 构建，这样您可以在升级 Nuxt 之前先迁移服务端代码（包括模块）。

无需修改配置。只需将 `nitro` 添加到依赖中：

::code-group{sync="pm"}

```bash [npm]
npm install nitro
```

```bash [yarn]
yarn add nitro
```

```bash [pnpm]
pnpm add nitro
```

```bash [bun]
bun add nitro
```

```bash [deno]
deno add npm:nitro
```

::

如果 `package.json` 中有 `nitro`，Nuxt 就会用 Nitro v3 构建。移除它即可切换回原来的版本。

![使用 Nitro v3 运行 nuxt build](/assets/blog/v4-7/nitro-v3-build-dark.png)

::caution
此功能仍处于**高度实验性**阶段。Nitro v3 仍是候选版本，现阶段没有稳定性保证。请在分支中试用，避免用于生产环境。🙏
::

欢迎试用 Nitro v3！在我们约有 170 个页面的基准测试应用中，同一个运行在 4.7 上的应用从 Nitro v2 切到 Nitro v3 后，在生成完全相同的 HTML 的情况下，首页每秒处理的请求数提升了 33%（从 926 到 1,236），包含 1,000 个链接的页面则提升了 44%（从 219 到 316）。

大多数 Nuxt 4 应用（以及它们使用的模块）都为 Nitro v2 和 h3 v1 编写。因此，Nitro v3 在 Nuxt 4 中通过名为 `nitroLegacy` 的兼容层运行。它让 `h3`、`nitropack` 和 `#imports` 的导入继续正常解析，保留 Nitro v2 的自动导入、`useRuntimeConfig(event)`、`event.node` 和钩子，也保留了许多 h3 v1 的行为，例如 `sendRedirect` 会结束响应以及缓存路由会发送 `cache-control` 标头。

确认应用正常运行后，可关闭兼容层，找出仍依赖它的代码：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitroLegacy: false,
})
```

使用 Nitro v3 时，仍有几处行为会发生变化。首先是路由规则，Nitro v3 使用[不同的模式语法](/docs/getting-started/upgrade#route-rule-patterns)匹配规则，因此 `/blog/*` 现在也适用于 `/blog/2026/hello`。Nuxt 会对每条含义发生变化的规则发出警告，遇到使用多个通配符的规则时（例如 `/api/*/items/**`）则会停止运行，可以用命名参数改写（`/api/:id/items/**`）。应用和服务端以相同的方式匹配路由规则，所以 `appMiddleware` 和 `ssr` 等 Nuxt 专用规则在两端适用的路径一致。

另一处变化是导入。若服务端代码导入了应用未声明的包，Nitro v2 会回退到 Nuxt 自身的依赖。Nitro v3 不再回退，因此 `nuxt dev` 会报错，例如 `Cannot find package 'ufo'`。请确认服务端代码导入的每个包都列在 `package.json` 中。

::read-more{to="/docs/getting-started/upgrade#testing-nitro-v3"}
查看 Nuxt 4 使用 Nitro v3 后的完整变更列表。
::

如果遇到问题（确实有可能），请[提交 issue](https://github.com/nuxt/nuxt/issues/new/choose)并注明 Nitro v3。每条反馈都有助于大家更顺利地迁移到 Nuxt 5。❤️

### Nuxt CLI 4.1 {#nuxt-cli-41}

Nuxt 4.7 也带来了 [Nuxt CLI 4.1](https://github.com/nuxt/cli/releases/tag/v4.1.0)。

最明显的变化在 `nuxt build`。CLI 现在通过一组新的构建钩子直接渲染整个生产构建过程，取代了逐个打印工具日志的方式（[nuxt/cli#1662](https://github.com/nuxt/cli/pull/1662)、[#37194](https://github.com/nuxt/nuxt/pull/37194)）。感谢 [@atinux](https://github.com/atinux) 的贡献。❤️ 所有构建器（Vite、webpack、Rspack、Rsbuild）和服务端构建器（Nitro v2、Nitro v3 和 `@nuxt/vite-server`）的显示方式都一致：

![Nuxt 4.7 中由 Nuxt CLI 4.1 运行的 nuxt build](/assets/blog/v4-7/build-after-dark.gif)

`nuxt generate` 也会以同样的方式显示已预渲染的路由，并在结束时给出部署建议：

![nuxt generate 列出已预渲染的路由](/assets/blog/v4-7/prerender-after-dark.png)

还有这些变化：

- `nuxt dev --https` 通过 HTTP/2 提供服务，因此浏览器可在同一连接上并行加载页面模块，感谢 [@ProgramRipper](https://github.com/ProgramRipper)（[nuxt/cli#1694](https://github.com/nuxt/cli/pull/1694)）
- 可以在开发面板的各个区域内点击和滚动，感谢 [@Flo0806](https://github.com/Flo0806)（[nuxt/cli#1665](https://github.com/nuxt/cli/pull/1665)）
- 只要终端支持，没有系统剪贴板也能复制 URL 或错误信息（例如在 SSH 或容器中）（[nuxt/cli#1693](https://github.com/nuxt/cli/pull/1693)）
- 为模块作者新增 `nuxt module build` 和 `nuxt module prepare` 命令（[nuxt/cli#1687](https://github.com/nuxt/cli/pull/1687)），为基于 `tsdown` 且支持 TypeScript 7.1 的 `@nuxt/module-builder` v2 做准备（敬请期待！）

- 从 [nitropack v2.14](https://github.com/nitrojs/nitro-v2/releases/tag/v2.14.0) 起，预渲染失败的路由会与链接到它的页面一同列出（[#37245](https://github.com/nuxt/nuxt/pull/37245)）

## 🤖 WebMCP（实验性） {#webmcp-experimental}

[WebMCP](https://webmachinelearning.github.io/webmcp/) 是一项浏览器 API 提案，允许页面向浏览器中的 AI agent 提供 _工具_。这样，agent 无需猜测要点击哪个按钮，就能把商品加入购物车或提交表单。

这项功能始于 [@sdras](https://github.com/sdras) 对 Vue 和 WebMCP 的提案，许多设计来自她的工作和反馈（[#37195](https://github.com/nuxt/nuxt/pull/37195)）。感谢 Sarah！💚

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    webmcp: true,
  },
})
```

agent 所需的大部分操作都已经绑定在模板中，因此只需用 `@tool` 标记函数：

```vue [app/pages/index.vue]
<script setup lang="ts">
const { data: products } = await useFetch('/api/products')
const cart = useCart()

/**
 * Add one of a product to the cart. Use when the user wants to buy something.
 * @tool
 */
function addToCart (sku: string) {
  cart.value.push(sku)
}
</script>

<template>
  <ul>
    <li v-for="product in products" :key="product.sku">
      {{ product.name }}
      <button :disabled="!product.inStock" @click="addToCart(product.sku)">
        Add
      </button>
    </li>
  </ul>
</template>
```

这会注册一个 `add_to_cart` 工具。参数来自模板，因此 agent 只能执行用户点击时能够执行的操作，按钮禁用时也无法调用。在 `v-for` 中，`:key` 成为 agent 可以选择的 `target`，共享的 `list_targets` 工具会列出屏幕上的目标。

将 `@tool` 绑定到 `@submit` 后就会得到一个表单工具。它以表单的 `v-model` 绑定作为输入，调用时会填充并实际提交表单，因此验证和提交处理函数会像用户亲自操作时一样运行：

```vue [app/pages/contact.vue]
<script setup lang="ts">
import { z } from 'zod'

const contactSchema = z.object({ email: z.email(), message: z.string().min(5) })
const form = reactive({ email: '', message: '' })

/**
 * Send a message to the shop. Use when the user has a question about an order.
 * @tool
 * @input contactSchema
 */
async function sendMessage () {
  await $fetch('/api/contact', { method: 'POST', body: form })
  return 'Sent.'
}
</script>

<template>
  <form @submit.prevent="sendMessage">
    <label>Email <input v-model="form.email" type="email"></label>
    <label>Message <textarea v-model="form.message" /></label>
    <button type="submit">Send</button>
  </form>
</template>
```

调用只能填写用户本来就能填写的字段。字段必须已渲染，且未被禁用或设为只读。`@tool` 后的标记描述操作（`readonly`、`consequential`、`confirm`、`values`），无法映射到单个控件的工具可用 `defineAgentTool()` 和 `useAgentTool()` 定义和使用：

```vue [app/pages/products.vue]
<script setup lang="ts">
import { z } from 'zod'

const searchProducts = defineAgentTool({
  name: 'search_products',
  description: 'Find products by name. Use when the user asks what is for sale.',
  input: z.object({ query: z.string() }),
  annotations: { readOnlyHint: true },
  execute: ({ query }, { signal }) => $fetch('/api/products', { query: { q: query }, signal }),
})

useAgentTool(searchProducts)
</script>
```

最后，`useAgentActivity()` 可向用户展示 agent 正在做什么，并允许用户停止操作：

```vue [app/components/AgentStatus.vue]
<script setup lang="ts">
const { current, stop } = useAgentActivity()
</script>

<template>
  <p v-if="current">
    {{ current.message }} <button @click="stop">Stop</button>
  </p>
</template>
```

::themed-video{light="/assets/blog/v4-7/webmcp-agent-run-light.mp4" light-poster="/assets/blog/v4-7/webmcp-agent-run-light.png" dark="/assets/blog/v4-7/webmcp-agent-run-dark.mp4" dark-poster="/assets/blog/v4-7/webmcp-agent-run-dark.png" controls loop class="rounded-lg"}
::

Nuxt 还会注册一个列出页面的 `navigate` 工具，对无法转换为工具的绑定（或不符合 Chrome [工具设计指南](https://github.com/GoogleChromeLabs/webmcp-tools)的描述）发出构建警告，并在开发时把每个访问过的页面的工具写入 `.nuxt/webmcp/schema.json`，供 [`webmcp-evals`](https://github.com/GoogleChromeLabs/webmcp-tools/tree/main/webmcp-evals) 使用。

::note
WebMCP 规范仍在演进，API 目前需要通过功能开关才能在 Chrome 中提前试用。在不支持它的浏览器中，不会注册任何工具，应用的行为与原来相同。
::

## 🔎 集中查看所有问题 {#all-your-problems-in-one-place}

- 启用 `typescript.typeCheck` 时的类型错误
- 加入 Vite 的其他检查器所报告的问题，例如 ESLint
- 过去容易在终端中被忽略的 Vue 编译器警告（[#36967](https://github.com/nuxt/nuxt/pull/36967)）
- Nuxt 扫描应用时发出的警告，例如组件名称重复或导入冲突（[#36969](https://github.com/nuxt/nuxt/pull/36969)）

每个来源对应一个「问题集」。徽章汇总问题总数，点击后会在页面侧边打开抽屉，按来源分组显示问题，并附上相关代码片段、规则文档链接，以及在编辑器中打开各个问题的按钮。

## 🩺 模板诊断 {#template-diagnostics}

Vue 编译器不了解应用中的页面或服务端组件，而 Nuxt 能获取这些信息。因此，Nuxt 现在会检查模板中几类需要了解应用结构才能发现的错误（[#36754](https://github.com/nuxt/nuxt/pull/36754)）：

- `<NuxtLink>` 的静态 `to` 未匹配任何页面（[`NUXT_B4025`](/docs/errors/b4025)）
- 在服务端组件上使用无法生效的 `v-on` 或 `v-model`（[`NUXT_B3014`](/docs/errors/b3014)）
- 将函数或类实例作为 prop 传给服务端组件（[`NUXT_B3015`](/docs/errors/b3015)）

![NuxtLink 指向不存在的页面时触发的 NUXT_B4025 警告](/assets/blog/v4-7/template-diagnostic-dark.png)

在开发环境中，修复前，每个打开的页面都会显示这些诊断（也会归为一个问题集）。该功能默认开启，可通过 `experimental.templateDiagnostics: false` 关闭。

## 🧯 服务端错误边界 {#server-side-error-boundaries}

`<NuxtErrorBoundary>` 过去只能捕获客户端错误。组件在服务端渲染时抛出的错误会绕过错误边界，直接转到错误页面。

启用 `experimental.ssrErrorBoundary` 后，它也能捕获服务端错误（[#36990](https://github.com/nuxt/nuxt/pull/36990)）：

```vue [app/pages/index.vue]
<template>
  <NuxtErrorBoundary>
    <BrokenWidget />
    <template #error="{ error, clearBoundaryError }">
      <p>Widget unavailable</p>
      <button @click="clearBoundaryError">
        Retry
      </button>
    </template>
  </NuxtErrorBoundary>
</template>
```

如果 `<BrokenWidget>` 在服务端抛出错误，响应状态仍是 `200`，页面的其余部分正常渲染，出错组件的位置则显示 `#error` 插槽。随后客户端会水合到同一状态。在生产环境中，非 HTTP 错误传入插槽时会变为普通的 `500` 错误，服务端错误消息不会出现在 HTML 中。

![一个组件在 SSR 时出错，其余部分正常渲染的页面](/assets/blog/v4-7/error-boundary-light.png){.dark:hidden}
![一个组件在 SSR 时出错，其余部分正常渲染的页面](/assets/blog/v4-7/error-boundary-dark.png){.hidden.dark:block}

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    ssrErrorBoundary: true, // enabled with `future.compatibilityVersion: 5`
  },
})
```

新增的 `retry-on-client` prop 会在 HTML 中渲染 `#error` 插槽，随后在浏览器中重试渲染原内容。这适用于只能在客户端运行的组件，可替代现已弃用的 `<NuxtClientFallback>`。

您可能也注意到，插槽现在暴露 `clearBoundaryError`（[#37079](https://github.com/nuxt/nuxt/pull/37079)）。它与 `clearError` 是同一个方法，改名是为了防止误用。如果忘记从插槽 props 中解构 `clearError`，模板会调用 _全局_ `clearError`，导致错误边界无法恢复。

## ✅ 运行时配置验证 {#validated-runtime-config}

以往运行时配置的类型由默认值推断，环境变量通过 `destr` 转换。因此，难以声明必填值或枚举，偶尔还会把 `4848e0` 这类看起来像数字的字符串转成数字。😬

现在，`runtimeConfig` 中的任意值都可以用 [Standard Schema](https://standardschema.dev) 描述，例如由 [Zod](https://zod.dev)、[ArkType](https://arktype.io) 或 [Valibot](https://valibot.dev) 定义的 schema（[#36905](https://github.com/nuxt/nuxt/pull/36905)）：

```ts [nuxt.config.ts]
import { z } from 'zod'

export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: z.string(), // required, so it must be set at runtime
    session: z.object({
      maxAge: z.number().int().default(60 * 60),
      secure: z.boolean().default(true),
    }),
    public: {
      mode: z.enum(['preview', 'production']).default('production'),
    },
  },
})
```

schema 决定类型，其中的默认值（如有）就是配置默认值。服务端启动时会将环境变量转换为对应类型。如果缺少某个值或转换失败，服务端会停止启动，并在一条错误消息中列出所有问题：

![列出缺失的运行时配置值的 NUXT_E8014 错误](/assets/blog/v4-7/runtime-config-error-dark.png)

schema 本身不会进入服务端构建产物。Nuxt 在构建时将它编译成一份简短的描述（包含类型、必填值、枚举和联合类型）。模块也可以通过 `updateRuntimeConfig()` 声明 schema。

未来可能会增加更多验证规则。目前仅保留少量规则，以确保服务端仍能快速启动。

::read-more{to="/docs/guide/going-further/runtime-config#validating-with-a-schema"}

::

## 🚀 性能 {#performance}

本次发布花了大量时间进行性能分析。以下是 4.7 与 4.6.4 在 [e18e 框架基准测试](https://github.com/e18e/framework-performance)的起始应用以及我们自己的基准测试应用上的对比：

| | v4.6.4 | v4.7.0 | |
| --- | --- | --- | --- |
| 已安装包数量，起始应用 | 523 | 473 | -50 |
| `node_modules`，起始应用 | 226.9 MB | 208.4 MB | -8% |
| 服务端构建产物，起始应用 | 2.17 MB | 1.23 MB | -43% |
| 首次页面加载，起始应用 | 80.4 kB，14 次请求 | 66.3 kB，3 次请求 | -18% |
| SSR 吞吐量，起始应用 | 245 请求/秒 | 292 请求/秒 | +19% |
| 首次内容绘制，起始应用（SSR） | 90.7 ms | 79.2 ms | -13% |
| SSR 吞吐量，含 1,000 个 `<NuxtLink>` 的页面 | 88 请求/秒 | 218 请求/秒 | 2.5 倍 |
| SSR 吞吐量，约有 170 个页面且启用 `staticRoutes` 的应用 | 890 请求/秒 | 1,976 请求/秒 | 2.2 倍 |
| 水合耗时，Nuxt UI 落地页 | 757 ms | 644 ms | -15% |
| 总阻塞时间，Nuxt UI 落地页 | 276 ms | 180 ms | -35% |

`nuxt build` 在大型应用中约快 7%，在起始应用中约慢 6%，`nuxt dev` 的启动速度与之前相同。以下是其他改进的来源。

### 更轻量的客户端 {#a-lighter-client}

当没有代码使用 `$fetch` 时，客户端构建产物会省去 `ofetch`（[#35790](https://github.com/nuxt/nuxt/pull/35790)）。客户端未操作页面 head 时，unhead 也会省去（[#37035](https://github.com/nuxt/nuxt/pull/37035)、[#37243](https://github.com/nuxt/nuxt/pull/37243)）。如果应用没有自定义 `error.vue`，unhead 会在渲染内置错误页面时一同加载，让最小应用的入口文件减少约 6 kB 的 gzip 体积。

`app.vue` 中对 `useHead()` 和 `useSeoMeta()` 的静态调用会被提升到服务端渲染器（[#37048](https://github.com/nuxt/nuxt/pull/37048)），因此 SPA 的初始 HTML 也包含这些内容。

Nuxt 在水合前发出的文件请求也更少了。在我们的 Nuxt UI 基准测试页面上，浏览器需要预先加载的 JavaScript 文件从 18 个减到了 6 个。

在生产环境的客户端构建中，具有静态内部 `to` 的 `<NuxtLink>` 现在会编译为普通的锚点元素，无需创建组件实例（[#36904](https://github.com/nuxt/nuxt/pull/36904)）。页面组件名称也会在构建时设置（[#36902](https://github.com/nuxt/nuxt/pull/36902)）。

### 更快的水合 {#faster-hydration}

在典型的营销页面上，水合的大部分开销来自 V8 在函数首次执行时才编译它们。Nuxt 现在会为入口、布局和页面代码块添加 [V8 编译提示](https://v8.dev/blog/explicit-compile-hints)，让 Chrome 在下载时就能在主线程之外编译（[#36758](https://github.com/nuxt/nuxt/pull/36758)）。该 PR 的测量结果显示，一个较重的落地页的水合耗时从 477 ms 降到 311 ms，总阻塞时间从 137 ms 降到 40 ms。

Nuxt 还会让浏览器先完成绘制再水合，并在启动阶段之间把控制权交还给浏览器，避免水合拉长一个长任务（[#36760](https://github.com/nuxt/nuxt/pull/36760)）。懒加载代码块会在应用就绪后才发出预取提示，避免与页面当前需要的资源争用（[#36794](https://github.com/nuxt/nuxt/pull/36794)、[#36878](https://github.com/nuxt/nuxt/pull/36878)）。

### 更快的服务端渲染 {#faster-server-rendering}

新增了可主动启用的 `experimental.staticRoutes` 选项（[#36867](https://github.com/nuxt/nuxt/pull/36867)）。默认情况下，Nuxt 会为每次服务端请求创建新的 vue-router 匹配器，以便应用在运行时添加路由。如果应用无需动态添加路由，可以在构建时声明路由固定：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    staticRoutes: true,
  },
})
```

服务端随后只构建一次路由匹配器。在我们约有 170 个页面的基准测试应用中，一个小页面的吞吐量增至两倍以上（从 890 到 1,976 请求/秒）。它还会启用 `early404`。相应地，`router.addRoute()`、`removeRoute()` 和 `clearRoutes()` 会抛出错误（并从 `useRouter()` 的类型中移除），因此应使用 `pages:extend` 钩子添加路由。

::tip
这个选项值得启用。如果不在运行时添加路由，就能直接获得性能提升。🔥
::

::read-more{to="/docs/guide/going-further/experimental-features#staticroutes"}
进一步了解 `staticRoutes`。
::

此外，渲染后的 HTML 现在会分块编码（[#36719](https://github.com/nuxt/nuxt/pull/36719)、[#36892](https://github.com/nuxt/nuxt/pull/36892)），效果相当明显。过去模板里的任何一个 `→` 都会使 V8 用双字节字符串编码整个文档。每次请求还有一些较小的性能优化（[#36890](https://github.com/nuxt/nuxt/pull/36890)）。

### 构建和开发 {#builds-and-dev}

- 启用 `experimental.viteEnvironmentApi`（或 `compatibilityVersion: 5`）后，客户端和服务端会同时构建，在起始应用上约快 11%（[#37047](https://github.com/nuxt/nuxt/pull/37047)），可以用 `experimental.parallelBuild: false` 关闭并行构建
- 自动导入的组件直接在 Vue 模板编译器中解析，省去了后续单独的处理步骤（[#36763](https://github.com/nuxt/nuxt/pull/36763)），而且延迟水合相关的 prop 现在也适用于 `<template lang="pug">` 🎉
- 启用 `experimental.decorators` 后，Babel 只处理实际包含装饰器的服务端文件，构建速度提升约 30%（[#37053](https://github.com/nuxt/nuxt/pull/37053)）
- 仅当项目中有 JSX/TSX 文件时，才加载 `@vitejs/plugin-vue-jsx`（以及 Babel）（[#37054](https://github.com/nuxt/nuxt/pull/37054)）
- 直接加载 `nuxt.schema` 文件，无需 `jiti`，耗时从约 100 ms 降至 3 ms（[#37027](https://github.com/nuxt/nuxt/pull/37027)）
- Vite 预打包依赖时会扫描每个层的应用目录，因此冷启动 `nuxt dev` 时页面重新加载的次数大幅减少（[#36777](https://github.com/nuxt/nuxt/pull/36777)）
- 在开发环境中，如果服务端重建时仍有请求正在渲染，该请求会继续用旧代码完成处理，避免返回 503，可通过 `nitro.devServer.drain` 调整这一行为（[#37245](https://github.com/nuxt/nuxt/pull/37245)）

特别感谢 [@onmax](https://github.com/onmax) 为本次发布提交了二十多个性能相关的 PR，涵盖转换过滤器、路由树复用，以及编辑组合式函数时保持 HMR 的速度。❤️

构建性能分析器也更准确了。它现在测量每个钩子占用的 CPU 时间，因此仅在等待的钩子不会再显示为开销最大的一项（[#37052](https://github.com/nuxt/nuxt/pull/37052)）。

### 按需安装 Nuxt DevTools {#nuxt-devtools-on-demand}

感谢 [@antfu](https://github.com/antfu)，`nuxt` 不再直接依赖 `@nuxt/devtools`（[#36581](https://github.com/nuxt/nuxt/pull/36581)），改为自带体积很小的 [`@nuxt/devtools-onboard`](https://www.npmjs.com/package/@nuxt/devtools-onboard)。如果已安装 Nuxt DevTools（v3 或 v4），Nuxt 会加载它。如果尚未安装，`nuxt dev` 会显示一个小按钮，点击后在终端确认即可安装。

这样首次安装 Nuxt 时的体积更小，您也可以选择 DevTools v3 或 v4。

## 🦀 Rsbuild 构建器 {#rsbuild-builder}

感谢 [@Nsttt](https://github.com/Nsttt) 带来新的 `@nuxt/rsbuild-builder`，它将构建交给 [Rsbuild](https://rsbuild.rs) 处理（[#36499](https://github.com/nuxt/nuxt/pull/36499)）。客户端和服务端分别使用 Rsbuild 环境，Vue 通过 `@rsbuild/plugin-vue` 处理，CSS 通过 Lightning CSS 和 PostCSS 处理。

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  builder: 'rsbuild',
})
```

它取代了已弃用的 `@nuxt/rspack-builder`（后者仍能运行，但会发出警告）。升级指南介绍了[如何切换](/docs/getting-started/upgrade#moving-to-the-rsbuild-builder)。模块可以使用 `extendRsbuildConfig()` 和 `addRsbuildPlugin()`，`addRspackPlugin()` 也能继续使用。

## 🧰 面向模块作者 {#for-module-authors}

### 渲染器插件 {#renderer-plugins}

有些模块需要在初始 HTML 中添加内容。例如，`@nuxtjs/color-mode` 会注入一段小脚本。`@nuxt/vite-server` 没有可用于注册插件的 Nitro，因此需要一种新的注册方式。

渲染器插件注册在渲染器上，所以能与任何服务端构建器配合使用（[#36601](https://github.com/nuxt/nuxt/pull/36601)）：

```ts [module.ts]
addRendererPlugin(resolve('./runtime/server/renderer'))
```

```ts [runtime/server/renderer.ts]
import type { RendererPlugin } from 'nuxt/server'

export default (({ hooks }) => {
  hooks.hook('render:html', (html) => {
    html.head.push(`<script>${script}</script>`)
  })
}) satisfies RendererPlugin
```

在较旧的 Nuxt 中，`addRendererPlugin` 会把同一个文件注册为 Nitro 插件。另有一个新的 `render:document` 钩子，在所有 `render:html` 监听器运行后，以非流式响应的完整 HTML 文档为参数调用（[#36989](https://github.com/nuxt/nuxt/pull/36989)）。

### 其他变化 {#and-more}

- 无论使用哪个构建器，`build:environment:start`、`build:environment:done` 和 `build:prerender:*` 钩子都会报告每个生产构建产物和预渲染路由（[#37194](https://github.com/nuxt/nuxt/pull/37194)）
- `updateRuntimeConfig()` 支持用 [schema](/docs/api/kit/runtime-config#schemas) 定义模块选项
- 新增 `extendRsbuildConfig()`、`addRsbuildPlugin()`，以及 `addBuildPlugin()` 的 `rsbuild` 变体
- `nuxt/server` 提供 `defineHandler`，并以 `defineEventHandler` 为别名，与 Nitro v3 一致（感谢 [@atinux](https://github.com/atinux)，[#36929](https://github.com/nuxt/nuxt/pull/36929)）
- 每个请求都使用 `nuxt.request` 追踪通道，让 APM 工具在使用任意服务端构建器时获得相同的 span 层级（感谢 [@logaretm](https://github.com/logaretm)，[#36483](https://github.com/nuxt/nuxt/pull/36483)）

## 🛠️ 其他改进 {#other-improvements}

`addRouteMiddleware` 现在会返回一个用于移除该中间件的函数（[#37080](https://github.com/nuxt/nuxt/pull/37080)）：

```ts [app/plugins/onboarding.ts]
export default defineNuxtPlugin(() => {
  const onboarded = useCookie<boolean>('onboarded')
  if (onboarded.value) {
    return
  }

  const unregister = addRouteMiddleware((to) => {
    if (to.path !== '/onboarding') {
      return navigateTo('/onboarding')
    }
  })

  watch(onboarded, (value) => {
    if (value) {
      unregister()
    }
  })
})
```

`onNuxtReady` 接受 `timeout`，避免回调被无限期推迟，也接受 `signal`，以便在组件先卸载时跳过仍在等待的回调（[#36743](https://github.com/nuxt/nuxt/pull/36743)）：

```ts
const controller = new AbortController()
onNuxtReady(() => { /* ... */ }, { timeout: 2000, signal: controller.signal })
onBeforeUnmount(() => controller.abort())
```

还有几项改进：

- `sourcemap: { client: 'nosource' }` 会生成不含原始源代码的 source map，因此可以安全地发布（感谢 [@0xgdr](https://github.com/0xgdr)，[#36534](https://github.com/nuxt/nuxt/pull/36534)）
- `<NuxtLoadingIndicator>` 新增 `finish-color` prop（同样感谢 [@0xgdr](https://github.com/0xgdr)，[#36533](https://github.com/nuxt/nuxt/pull/36533)）
- `navigateTo(url, { open })` 可以默认传入 `noopener`，防止打开的页面通过 `window.opener` 访问原页面。`compatibilityVersion: 5` 默认开启此行为，也可以设置 `experimental.defaults.navigateTo.noopener: true`（[#37075](https://github.com/nuxt/nuxt/pull/37075)）
- `nuxt/app` 导出 `NuxtLinkSlotProps`（感谢 [@VividLemon](https://github.com/VividLemon)，[#37092](https://github.com/nuxt/nuxt/pull/37092)）
- `serverFetch` 根据服务端路由推断类型（[#36543](https://github.com/nuxt/nuxt/pull/36543)）
- 使用 Nitro v3 时，所有请求共享同一个运行时配置对象，因此在开发环境中，如果服务端渲染期间修改了该对象，Nuxt 会发出 `NUXT_E1014` 警告（[#37076](https://github.com/nuxt/nuxt/pull/37076)）
- 当 Node.js 需要将 `nuxt.config` 作为 ESM 重新解析时，Nuxt 会建议在 `package.json` 中添加 `"type": "module"`（[#37205](https://github.com/nuxt/nuxt/pull/37205)）

## 🩹 修复 {#fixes}

本次发布和以往一样包含许多修复。其中，[@pawell67](https://github.com/pawell67) 让 `callOnce` 在执行过程中离开页面后能够再次运行，并让 Nitro 在真正读取请求体时才创建请求体流（[#37149](https://github.com/nuxt/nuxt/pull/37149)、[#37129](https://github.com/nuxt/nuxt/pull/37129)），[@astraldev](https://github.com/astraldev) 让流式响应开始前设置的 Cookie 能到达浏览器，并让仍在等待的页面保持加载状态（[#37131](https://github.com/nuxt/nuxt/pull/37131)、[#37165](https://github.com/nuxt/nuxt/pull/37165)），[@waleedtariq109](https://github.com/waleedtariq109) 让延迟水合重放触发它的交互（[#36838](https://github.com/nuxt/nuxt/pull/36838)），[@lafllamme](https://github.com/lafllamme) 让共享预渲染数据读取失败时在后续路由中重试，避免用 `null` 预渲染这些路由（[#37244](https://github.com/nuxt/nuxt/pull/37244)），[@posva](https://github.com/posva) 则让重新加载时保留浏览器恢复的滚动位置（[#36957](https://github.com/nuxt/nuxt/pull/36957)）。

## 🔒 安全性 {#security}

本次发布修复了三个安全问题。我们建议升级。

- **`_payload.json` 的路由规则**（[GHSA-jxc9-w3j6-pwp2](https://github.com/nuxt/nuxt/security/advisories/GHSA-jxc9-w3j6-pwp2)，中危）。如果同时为页面设置带通配符的 `cache`、`swr` 或 `isr` 路由规则和一条更具体的规则，就会受到影响，例如对经过身份验证的区域设置 `cache: false`，或设置 `redirect`、`proxy` 或 `headers`。页面的 `_payload.json` 请求可能仅匹配通配符规则，导致一位用户的页面数据被缓存并提供给另一位用户。
- **通配路由中的编码斜杠**（[GHSA-vrh2-cfcx-c3fg](https://github.com/nuxt/nuxt/security/advisories/GHSA-vrh2-cfcx-c3fg)，中危）。[GHSA-f3x9-2chm-73c8](https://github.com/nuxt/nuxt/security/advisories/GHSA-f3x9-2chm-73c8) 的修复尚不完整。如果使用路由规则（例如 `appMiddleware`）控制 `pages/[...slug].vue` 这类通配页面，就会受到影响。路径中重复的编码斜杠或开头的编码斜杠可能绕过路由规则。
- **开发服务器的运行时配置**（[GHSA-h5xj-x893-p5f7](https://github.com/nuxt/nuxt/security/advisories/GHSA-h5xj-x893-p5f7)，低危，仅影响开发环境）。如果在不受信任的网络可访问的环境中运行 `nuxt dev`，就会受到影响。私有运行时配置可能会从早期的 Nitro 构建产物中被读取。

感谢 [inanna-malick](https://github.com/inanna-malick)、[stilwel](https://github.com/stilwel)、[kanokwut](https://github.com/kanokwut)、[onur-yuksekkaya](https://github.com/onur-yuksekkaya)、[DicksonWu654](https://github.com/DicksonWu654) 和 [rexpository](https://github.com/rexpository) 以负责任的方式报告这些问题。💚

::important
如果在包含用户专属数据的页面上使用 `cache`、`swr` 或 `isr` 路由规则，请在升级后清除可能已经缓存了 `_payload.json` 的 CDN 或边缘缓存。
::

## ⚠️ 升级前须知 {#heads-up-before-upgrading}

以下改动预计不会影响应用的正常运行，但值得留意：

- **Nuxt DevTools 不再随 Nuxt 安装。** 如果要使用它，请将 `@nuxt/devtools` 加到 `devDependencies`（或点击 `nuxt dev` 中显示的按钮）。
- **应用的 `vue` 低于 Nuxt 所需版本时会发出警告**（`NUXT_B7042`）。Nuxt 4.7 要求 `vue` `^3.5.46`，`npx nuxt upgrade --dedupe` 会同时更新 Vue 和 Nuxt。
- **模板诊断已启用。** 指向不存在的页面的链接可能会触发新的 `NUXT_B4025` 警告。如果链接指向服务端路由、`public/` 中的文件或其他网站，请添加 `external` prop。
- **启用 `experimental.viteEnvironmentApi` 时，客户端和服务端并行构建。** 如果某个 Vite 插件在构建服务端时读取客户端构建产物，请设置 `experimental.parallelBuild: false`。
- **仅当有代码使用 `globalThis.$fetch` 时，才会在客户端注册它。** 如果通过 Nuxt 在构建时无法检测到的方式读取它（例如在浏览器控制台、内联脚本或 `public/` 中的文件里），请设置 `experimental.globalFetch: true`。
- **`@nuxt/rspack-builder` 已弃用**，请改用 `@nuxt/rsbuild-builder`。
- **`<NuxtClientFallback>` 已弃用**，请改用 `<NuxtErrorBoundary retry-on-client>`。
